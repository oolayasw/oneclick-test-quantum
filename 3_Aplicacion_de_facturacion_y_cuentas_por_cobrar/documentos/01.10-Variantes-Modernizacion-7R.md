## Contexto para la Selección de Variantes

### Factores determinantes

1. **No existe path de migración para jQuery 1.12 → moderno** — jQuery no se "actualiza" a React/Vue, se reemplaza. Esto descarta Refactor puro.
2. **localStorage no es una base de datos** — no tiene migración a cloud managed. Requiere reemplazo por BD real + backend.
3. **1,272 LOC hacen viable un Rebuild** — el codebase es tan compacto que reescribir es más rápido que intentar parchear.
4. **Lógica de negocio clara y extraíble** — 5 dominios, 15 reglas, state machine explícita. Se puede reconstruir con fidelidad.
5. **0 integraciones externas** — no hay contratos con sistemas externos que preservar, eliminando riesgo de incompatibilidad.

### Variantes descartadas y razón

| Variante | Razón de descarte |
|---|---|
| Retire | App activa con funcionalidad de negocio necesaria (facturación). No se puede apagar. |
| Retain | Riesgo de seguridad activo (22 XSS, sin auth) + datos perdibles. Retener es negligente. |
| Rehost | No hay servidor que "re-hostear". App es archivos estáticos. No aplica el concepto. |
| Replatform | No hay plataforma que "re-platformear". Sin backend, sin BD, sin framework migratable. |
| Refactor | jQuery 1.12 no tiene refactoring path a moderno. Sin módulos, sin tests — refactoring es imposible sin safety net. |

### Variantes seleccionadas

Dado el score bajo (42.9), el stack obsoleto sin path de migración, y el tamaño compacto (1,272 LOC), las únicas variantes viables son **Rebuild** (reescritura completa) y **Rearchitect** (rediseño arquitectónico). Ambas implican código nuevo, pero difieren en el nivel de diseño previo y la arquitectura target.

## Variante 1: Rebuild Modular (RECOMENDADA)

### Descripción

Reescritura completa de la aplicación usando stack moderno (propuesta: Node.js + React + PostgreSQL). Se preserva el 100% de la funcionalidad actual (12 features, 5 dominios, state machine) pero se implementa desde cero con arquitectura correcta, autenticación real, BD real y CI/CD.

### Estrategia de Ejecución

| Fase | Semanas | Actividades |
|---|---|---|
| 0. Advisory + Alignment | 1-2 | Workshop A2, definir target stack, export datos localStorage, characterization tests |
| 1. Foundation | 2-3 | Backend API (Node.js/Express), BD (PostgreSQL), Auth (JWT), CI/CD pipeline |
| 2. Core Business | 4-6 | Facturación + Pagos + Cartera + State Machine |
| 3. Supporting | 7-8 | Notas crédito + Anulación + Dashboard + Auditoría |
| 4. Hardening | 9-10 | Tests E2E, seguridad, observabilidad, deployment producción |

### Ventajas

- Stack completamente moderno y mantenible a 5+ años
- Elimina 100% de la deuda técnica actual (los 18 hallazgos)
- Arquitectura correcta desde el inicio (capas, módulos, tests)
- Sin riesgo de regresión por compatibilidad con código viejo
- Habilita escala multi-usuario, multi-dispositivo, cloud

### Desventajas

- Requiere descubrimiento funcional (characterization tests para capturar comportamiento exacto)
- Mayor costo inicial que un "parche" (pero menor costo total a 2 años)
- Período de transición donde coexisten ambas versiones

### Riesgos específicos

| Riesgo | Probabilidad | Mitigación |
|---|---|---|
| Funcionalidad perdida (regla no documentada) | Media | Characterization tests exhaustivos como Fase 0 |
| Scope creep (features nuevas durante rebuild) | Media | Contrato con paridad funcional como baseline |
| Rechazo de usuarios al cambio de UI | Baja | Preservar flujos existentes, solo modernizar look & feel |

### Prerrequisitos

- Sponsor confirmado con presupuesto para talla S
- Al menos 1 SME funcional disponible para validación
- Decisión de target stack (workshop A2)
- Export de datos actuales de localStorage

## Variante 2: Rearchitect a Microservicios (ALTERNATIVA AMBICIOSA)

### Descripción

Rediseño completo de la arquitectura: separar en microservicios por dominio (Facturación, Pagos, Cartera, Ajustes, Reporting), cada uno con su propia BD y comunicación via eventos. Frontend como micro-frontend o SPA monolítica que consume APIs.

### Estrategia de Ejecución

| Fase | Semanas | Actividades |
|---|---|---|
| 0. Advisory + DDD | 2-3 | Event Storming, bounded contexts, contracts, target arch |
| 1. Platform | 3-5 | API Gateway, Auth service, Event bus, CI/CD per service |
| 2. Services | 5-10 | 5 microservicios (1 por dominio) + BD por servicio |
| 3. Frontend | 8-12 | SPA moderna consumiendo APIs |
| 4. Integration | 12-14 | Testing E2E, observabilidad, deployment |

### Ventajas

- Escalabilidad independiente por dominio
- Equipos pueden trabajar en paralelo por servicio
- Resiliencia (si un servicio cae, los otros operan)
- Arquitectura preparada para crecimiento futuro

### Desventajas

- **Sobre-ingeniería para 1,272 LOC** — microservicios para una app de 3 archivos es desproporcionado
- Mayor costo operativo (5+ servicios que gestionar vs 1)
- Mayor complejidad (event bus, consistency eventual, service discovery)
- Requiere equipo con experiencia en arquitectura distribuida
- Duración 14-16 semanas vs 10-12 de la Variante 1

### Riesgos específicos

| Riesgo | Probabilidad | Mitigación |
|---|---|---|
| Complejidad accidental mayor que la necesaria | Alta | Evaluar si el volumen justifica la distribución |
| Equipo sin experiencia en microservicios | Media | Incluir arquitecto senior en el equipo |
| Costo operativo mayor que el beneficio | Alta | Monitorear TCO vs monolito moderno |

### Prerrequisitos

- Todo lo de Variante 1 PLUS:
- Arquitecto senior con experiencia en event-driven
- Infraestructura cloud con orquestación (K8s o similar)
- Presupuesto para talla M (mayor que S)

## Recomendación

**Variante 1: Rebuild Modular** es la recomendada. Justificación:
- 1,272 LOC no justifican la complejidad de microservicios
- Un monolito modular moderno (capas bien separadas) es perfectamente mantenible a este tamaño
- Si en el futuro la app crece significativamente, la arquitectura modular permite extraer servicios (Strangler Fig)
- Menor costo, menor riesgo, menor duración, menor equipo necesario
